In an internal test, we stopped a notification worker just after it called the email provider. When the worker restarted, it picked up the same job and sent the same notification again.

The queue was doing exactly what we had asked: retry work that had not been marked complete. Our application had treated “send email” and “record delivery” as if they were one operation. They were not.

That failure became the starting point for a new delivery path.

## Record the event with the update

When someone publishes an update, we now write a notification event in the same database transaction. A separate worker reads these pending events and expands them into delivery jobs.

This outbox pattern closes one gap: a successfully published update cannot lose its notification event merely because the process exits before it reaches the queue.

It does not make delivery exactly once. We still have to handle retries beyond the database boundary.

## Give each delivery a stable identity

A delivery key combines the event, recipient, and channel. A database uniqueness constraint prevents two workers from creating separate delivery records for the same combination.

We pass a stable idempotency key to the email provider as well. Within the provider's supported retention window, repeating a request returns the earlier result instead of sending again. Outside that window, we cannot make the same guarantee. Ambiguous old attempts go to review rather than an unlimited automatic retry.

## Check access when the job runs

Queueing a notification is not permission to disclose its contents forever. Before sending, the worker checks that the recipient still belongs to the workspace and can access the project.

If an update was deleted or access changed, we skip delivery. The record says why, which is much more useful during debugging than a generic “success.”

## Make the failure paths visible

We now distinguish queued, accepted by provider, failed, and skipped. Provider acceptance is not proof that a person received or read an email.

The extra states make the system slightly less tidy on a diagram. They make it much easier to answer the practical question: what happened to this notification, and is it safe to try again?
