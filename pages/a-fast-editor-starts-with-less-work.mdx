Our early editor felt fine with a short paragraph. Paste in a long project update, add a checklist, and start moving between sections, and the experience became uneven.

The first instinct was to optimize the editor. Profiling pointed somewhere less interesting: work we had attached to every change event.

We were serializing the full document, preparing a preview, and scheduling a remote save more often than we needed to. Typing was paying for all of it.

## Keep the immediate path small

An edit now updates the document state and the visible editor first. The work required to keep the cursor and text correct stays on that path. Persistence and preview generation happen separately.

We still save a local recovery copy regularly. We batch nearby changes to avoid repeatedly serializing the same document while someone is typing quickly, and use a maximum interval so continuous typing cannot postpone recovery saves indefinitely.

The status indicator reflects completed writes. We do not show “Saved” merely because a save has been scheduled.

## Save changes, not keystroke requests

Remote saves are debounced and carry the draft's revision. If a save is already in flight, newer edits remain pending for the next request rather than launching an overlapping write.

A failed request leaves the draft visibly unsynced. It does not clear the pending state or replace the user's current text with the last server response.

That behavior is becoming especially important as we add support for intermittent connections.

## Treat pasted content as a separate workload

Pasting a long document is different from typing a character. We test it separately, along with large selections, undo, checklist edits, and keyboard navigation.

We also test composition input. A formatting shortcut must not interfere with an input method while someone is composing a character. An editor that feels fast only on one keyboard is not finished.

## Measure the whole interaction

We are watching input responsiveness and long tasks, not just the time it takes to save. A fast server cannot rescue an interface that blocks the next keystroke.

The result is a less ambitious change handler and a more dependable editor. There is still performance work ahead, but we now know which work belongs between a key press and the next frame—and which work can wait.
